# GPU Lab audit: 6 November 2026

This audit fixes host discovery and refusal handling and records bounded game observations. It does not qualify a new rendering binary. The v0.3.1-saros-effects-beta release assets are unchanged.

## Verified host fixes

- Mounted games in sandbox slots `_001` through `_009` were missed by the Python installer. Discovery now searches the same ten numbered slots as the native scanner, plus the existing `pfsmnt` location. A directory called `eboot.bin` is rejected.
- Non-object JSON game metadata could raise an exception; missing or non-string versions could escape the unreadable-metadata result. These cases now return `unreadable`.
- Truncated or malformed SFO key/data offsets could raise an exception or return truncated text. Parsing now checks the entry table, string bounds, declared capacity, format and terminators, and rejects ambiguous target entries.
- Invalid payload-manager JSON and malformed process rows could crash the write gate or satisfy an incomplete identity check. The gate now refuses malformed documents, missing/invalid process IDs, duplicate IDs and empty names before checking kernel/SceShellUI presence and active applications.

The new regression cases reproduced failures against the previous implementation. All **81 Python tests** pass after the fixes. Native metadata tests, app tests (including 9,605 resolution-planner comparisons), payload tests (including 107 swap cases) and the public-tree/site check also passed locally. Host simulations do not establish console rendering correctness.

An earlier host-only reset experiment exists, but its state-page ownership, initialization and concurrency are unqualified. Camera-cut handling, reactive inputs and sharpening also remain open. Quality mode remains stock FSR2.

## SAROS: fresh-boot Lite comparison failed before gameplay

The earlier Test5 startup qualification is recorded in [SAROS startup](SAROS-START-HERE.md). For the comparison, the regular PS5 on firmware 11.60 was restarted and the user ran only the existing jailbreak. Before loading payloads, the manager showed an empty load history, disabled autoload and no active game. FTP and kernel-log support services were loaded, then **one ShadowMount+ 1.7-beta5fix1** and **one mainline K-Stuff Lite v1.11**. Test5 was not loaded on this boot. The payload journal and manager events each record one request for each payload.

The installed Lite file was rehashed before loading: 1,737,080 bytes, SHA-256 `ab9a6cb4d3b1daf139d4d646e402b1cf569071acd64599c936d7a3a6164dc779`. ShadowMount matched the hash in the startup guide and reported successful startup/synchronization. Lite's daemon appeared and its shell patch message was logged; this does not prove all its kernel patches succeeded.

GPU Lab selected SAROS PPSA07631 01.000.000, HelixSR On, using the unchanged installed effects-on package. The handoff recorded `state=helix`, `moves=0`, `ok=1`, followed by the shell launch request. SAROS remained at its splash screen; a complete process-list check showed no running `eboot`. The captured log then showed `l2p_read_decrypt_icv_outer`, `ppfs_read_nsid2_icv`, and `mountppfs` errors with errno 5, followed by repeated storage read/write errors. Remote Play later showed black. Further console operations were stopped and local recovery requested. No successful normal close, fresh mounted-executable hash or gameplay measurement was obtained in this arm.

This is a failed startup observation for this exact boot/package/payload combination. It does not isolate a universal Lite defect, establish physical SSD failure or identify a proven patch. There was no second kernel injection, game-file rewrite, rendering fallback or change to shadows/fog. This control arm remains a failed startup observation. The subsequent bridge qualification below records a successful Lite setup.

Primary source review: [Lite v1.11 source](https://github.com/EchoStretch/kstuff-lite/tree/85fb88a526e58e357d6f1e626ce05af4acdb8b5d) already contains PPR/plaintext-related support, so “Lite has none” is incorrect. Its static profiles differ from Test5's reported dynamic Native/PLAINTEXT_NOAUTH installation/readback. [PPR read-path documentation](https://github.com/drakmor/ppr-patch/blob/main/PPR_READ_PATHS.md) helps frame that hypothesis; the failed boot does not prove that this difference caused the failure. [Issue 92](https://github.com/EchoStretch/kstuff-lite/issues/92) describes a different mounting scenario and is not confirmation of this cause.

## SAROS: A53-only bridge restores the tested Lite setup

After local recovery and a new jailbreak-only boot, the manager again showed empty history, disabled autoload and no running game. One A53-only bridge ran to completion, then one ShadowMount+ and one copy of the same original Lite v1.11. The full Test5 K-Stuff payload was never loaded on this boot. The bridge reused the exact owner-provided Test5 A53 initializer, replaced its main with a strict 11.60 check and one initializer call, and erased the embedded Test5 K-Stuff kernel image. This is a local binary adaptation, not an upstream Lite release or a source rebuild of the A53 implementation.

The bridge reported stock/native A53 state, installed through READMEM, read back all 72 PPR words and restored GET_MMU. SAROS passed both PPR mounts. The normal GPU Lab Triangle launch reached interactive gameplay with camera/movement response. The native mounted SELF matched SHA-256 `6797e08fe14354bb21b8c0de39e27b8222eeaf712fa4f61c5f170598c389ef11`. A second launch on the same boot also reached gameplay and responded to camera input. Both sessions closed normally; the final full list showed 82 processes and no eboot, with FTP and Payload Manager reachable.

Captured candidate logs did not contain the previous errno 5 / IOD / storage I/O failure pattern. All-zero ICV and NOT SIGNED MODE messages still occur during successful mounts and must not alone be treated as the old failure. This supports the missing A53 initialization as the compatibility dependency for this exact setup; it does not establish compatibility for every game or diagnose every possible Lite failure. See [exact hashes, provenance, build method and boot order](lite-1160-compat.md). Rest-mode/resume is unqualified, and no new FPS or image-quality claim is made.
